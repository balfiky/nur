1. The idea

Nūr started from a practical observation: many LLM assistants can sound emotionally responsive, especially when a prompt gives them a personality and memory, but the response often still feels like styling on top of the current conversation. The state does not always feel like it has depth, history, tension, or consequence.

The design question is: what if emotional behavior is not only prompted, but carried by explicit state? Nūr treats emotion as persistent internal variables, relationship history, unresolved loops, and self-observation. The LLM still writes the final language, but it receives context from a cognitive layer that changes over time.

Core thesis
State should persist, decay, and remain inspectable. A response after history should be shaped by accumulated context, not only by a fresh prompt.
Honest scope
This is a research prototype. It does not prove human-likeness, consciousness, therapeutic value, or psychological validity.

2. Theory stance

Nūr is inspired by PSI Theory, ACT-R, and CLARION, but it is not a faithful implementation of any of them. The project borrows engineering ideas: continuous state, decay, activation-weighted memory, fast/slow deliberation, and explicit internal traces. It does not implement formal drive systems, ACT-R production rules, or CLARION's full implicit/explicit learning architecture.

The point is not to claim psychological correctness. The point is to build an inspectable architecture where emotional continuity can be tested, ablated, and criticized.

3. Architecture

There are two runtime hosts: nur for console/Telegram/debug runtime, and nur-web for FastAPI, web UI, legacy endpoints, and the versioned /v1 API. Both feed into the same session manager and cognitive pipeline.

Runtime architecture: two hosts, one shared session/cognition layer, explicit persistence and tool boundaries.

4. Single-turn flow

One user message runs through deterministic state updates, memory retrieval, optional deliberation, optional tool handling, defense shaping, response strategy selection, final generation, self-check, and post-processing. The common case uses one LLM call. Optional paths can add calls; there is no fixed safe upper bound because inner-dialogue parsing can retry.

Single-turn flow: actual pipeline order, including gates and LLM-call accounting.

5. Memory and persistence

Nūr separates per-user data from the assistant's shared self-model. Per-user data lives under data/<platform>_<user_id>/, including nur.db and session JSON files. The shared self-model lives under data/shared/self_model.db.

Memory and persistence: per-user deletion wipes user data while preserving the assistant self-model by design.

6. Auth and tool safety

The public launch blockers found during validation were not in the cognitive layer; they were in packaging, auth coverage, and tool safety. Those were fixed before publication readiness: install works, legacy endpoints honor the bearer token when api_key is set, tools are off by default, filesystem tools are sandboxed, and shell execution requires a separate opt-in flag.

Safety boundary: HTTP auth and local side-effect tools are independent switches.

7. Evaluation

The current evaluation is structural, not human-subject evaluation. Phase 11 scenarios check whether the system selects expected strategies, moves modulators in expected directions, writes or closes relationship memory, and produces valid debug state. They do not grade whether a human finds the response emotionally convincing.

Evaluation harness: explicit backend selection, fresh scenario pipelines, instrumented LLM-call counting, and provenance-stamped reports.

8. What the evidence supports

The strongest current result is narrow but useful: relationship memory is load-bearing for the two cross-turn structural scenarios that require open-loop tracking. Disabling it breaks exactly those two scenarios and causes no unexpected failures. Other components are present but not falsifiable by this scenario suite.

Claim map: the current evidence supports one load-bearing component; other claims are explicitly scoped.

Do not overclaim this result. It does not prove human-likeness. It does not prove that inner dialogue or defense mechanisms are useless. It says the current structural suite can falsify relationship memory and cannot yet falsify the other components.

9. How to run it

The intended quick path is:

git clone https://github.com/balfiky/nur.git
cd nur
python3 -m pip install -e ".[dev]"
nur-web

Then open http://localhost:8000. The tracked config starts in mock mode, so a first run does not need an API key. For terminal use, run nur. For offline structural evals, run:

python3 -m evals --backend mock --tag phase11

10. Limitations

  • No prompt-only baseline yet. The current scenarios test internal structural behavior, so a fair prompt-only baseline needs a different scenario design.
  • No blinded human study yet. Human-likeness and emotional quality remain future work.
  • Token, retry, and cost telemetry are intentionally null until client-level instrumentation is implemented.
  • Telegram live bot behavior needs real end-to-end validation with a throwaway bot token before being advertised as a polished demo path.
  • WhatsApp is not implemented or claimed.
  • OpenClaw inspired the initial thinking, but Nūr does not integrate with OpenClaw and does not depend on it.
